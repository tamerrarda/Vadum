# Stream B — questions and change requests

Append-only. Reconciled into `02-OPEN-QUESTIONS.md` at integration. Requests for changes outside
`packages/wire/**` and `packages/client/**` go here; keep coding against the frozen interface meanwhile.

## 2026-09-12 · B5 is blocked

`plan/32-MEASUREMENT-METHOD.md` does not exist, so `wire/measure.ts` was **not** implemented —
`41-STREAM-B` B5 says not to start without it, and `25-SPEC-wire-api.md` says the methodology must be
written first (WIRE-6, an owner decision). Nothing else in Stream B depends on it: `renderQr` already
returns the version, EC level, matrix size and segment mode the report needs, and the scanner reports
which engine produced every read, so the data the method will ask for is already observable.

## 2026-09-12 · Spec gaps met while implementing wire and client

| # | Gap | What the code does | Needs a spec change? |
|---|---|---|---|
| B-1 | `26-SPEC`'s `VadumRpc` is read-only, but `Pool.create`, `Pool.close` and `submit` have to **send** a transaction, and no other seam exists. Stream C cannot supply one either — it owns apps, not RPC | `VadumRpc` gained `sendSetup(instructions, signers)`, `sendPayment(wireTransaction, lifetime)` and `getBalance(address)`. `sendPayment` picks the durable-nonce confirmer on the nonce path and the blockhash one on the fresh path (SOL-15), so no caller can get that wrong | **Yes, requested:** record the send surface in `26-SPEC`. The alternative — passing a kit client around — puts transaction plumbing in the apps |
| B-2 | `SubmitOutcome.settled` requires `newNonceValue: Nonce`, but a fresh-path payment has no nonce account | Widened to `Nonce \| null`: null on the fresh path, and null when the slot cannot be read after settlement. A `NONCE_RETURN` is only issued when it is non-null | **Yes, requested:** the field is unfillable as typed |
| B-3 | `status()`, `get()` and `list()` are synchronous while `KeyValueStore` is asynchronous, so something has to read the store first | `Pool`, `Queue` and `MintCache` each gained `load()`. `Pool.status()` throws `NONCE_LEDGER_MISSING` before it is called, which is also the state Stream C's RECOVERY screen keys on | No — confirm |
| B-4 | No code covers encoder-side misuse: an intent handed to the wrong encoder, a dynamic intent with no amount, an amount that does not fit the 8-byte field, a 32-byte field that is not 32 bytes | `WIRE_UNEXPECTED_TYPE` names both types; `WIRE_STATIC_CONSTRAINT` carries a `reason`; `WIRE_LENGTH_MISMATCH` covers both field-width failures | No |
| B-5 | `decodeAuth` needs `DecodeContext.intentFlags` for rule 6, and the spec does not say what happens without it | `WIRE_FLAGS_MISMATCH` with a `reason`. It fails closed: comparing the payload's flags against themselves would check nothing | No — confirm |
| B-6 | `MINT_UNKNOWN` means "absent from the local cache", so the RPC-side failures have no code: the mint account does not exist, its owner is not a token program, or it was fetched with `base64` instead of `jsonParsed` | `MINT_INCOMPATIBLE` with `blockers: []` and a `reason`, matching what `core.evaluateMint` does for a malformed shape (Stream A's A-5) | Maybe — one code for "this account is not a usable mint" would read better |
| B-7 | `Pool.estimateSetupCost` must report the setup fee, and there is no way to price a message that does not exist yet | `LAMPORTS_PER_SIGNATURE = 5_000n` × one signature, the figure Phase 0 measured, exported as a constant rather than buried | No — confirm. If v1 ever adds a priority fee this has to become an RPC call |
| B-8 | `Pool.close` leaves the pool record behind, and the spec does not say what state its slots are in | Every slot becomes `state: 'unknown'`, `value: null`. A closed pool is not a missing ledger: `NONCE_LEDGER_MISSING` stays reserved for a lost store (T7, D32) | No — confirm |
| B-9 | `reconcile` has no case for a slot whose account has been **closed** while a payment was pending | Counted as `released`, with the slot left `unknown`: the payment can never settle, so holding the slot spent forever would punish the payer for the merchant's silence | No — confirm |
| B-10 | `Queue.accept` enforces five rules and the spec does not order them | Dedupe (rule 13) → the T1 pre-check → the failed-send counter → the receipt cap → the exposure cap. Dedupe first so a replay is never reported as a cap breach | No — confirm |
| B-11 | `Queue.drain` eligibility is unspecified for a payment that already failed | `queued` and `failed` are retried, `submitting`, `settled` and `voided` are not. `expire` voids anything past the send window first | No — confirm |
| B-12 | `queueExposureCap` is written as the **T2** cumulative offline amount (31-PARAMETERS), but `Queue` sees all three tiers | `exposure()` counts unsettled **T1 and T2** payments, and the cap is not applied to T0. A T0 merchant hands over only after settlement, so a queued T0 payment is not exposure — counting it would block a large online sale on an offline cap | No — confirm |
| B-13 | `Queue.accept`'s `precheck` is optional, and a verdict that has crossed a store or a message boundary arrives as `null`, not `undefined` (the negative fixture passes `null`) | The parameter accepts `NonceVerdict \| null`; both mean "no verdict", so a T1 nonce-path acceptance still fails with `LIMIT_PRECHECK_REQUIRED` | No |
| B-18 | D38 covers funding a pool, but not **closing** one. A fee payer must still be rent-exempt after its fee is deducted, and the lamports the withdrawal credits in the same transaction do not count — so a payer left at exactly `getRentExemption(0)` by `create` cannot close its own pool. Devnet rejected it with "Transaction results in an account (0) with insufficient funds for rent" | `Pool.close` now checks the payer can pay the fee and stay rent-exempt, and raises `NONCE_POOL_UNDERFUNDED` with that reason instead of letting the chain refuse it. `estimateSetupCost` documents that a payer intending to close later funds `walletMinimum + fee` | **Yes, requested:** D38 and `26-SPEC`'s `estimateSetupCost` should say that the wallet floor is not enough to pay a later fee. It is the same trap as Phase 0 step 2, one transaction further on |
| B-17 | The public devnet websocket refused every connection during the verification run, so `sendPayment` could not confirm through kit's factory at all | The factory stays the primary path, exactly as `26-SPEC` mandates. **Only** when the channel fails to open does it fall back to broadcasting over HTTP and polling `getSignatureStatuses`. The transaction is already signed, so its signature is fixed and a second broadcast is a no-op; a merchant that cannot confirm cannot hand over | No — confirm. SOL-15's point is that the *blockhash confirmer* must never be used for a durable-nonce transaction, and the fallback uses neither confirmer |
| B-16 | Nothing in the spec says what a client does about rate limiting, and the devnet run died on `HTTP error (429)` twice — once on a read, once inside kit's confirmer | Every read, the setup broadcast and the confirmation poll retry with exponential backoff (up to 5 attempts) on 429 and 5xx, and on a dropped socket. kit's confirmer retries nothing, so a throttled or socket-less payment send falls back to the HTTP broadcast-and-poll path, which does. A `VadumError`, or anything the chain decided, is never retried | No — confirm. A public endpoint is the default for both apps, so this is product behaviour, not test scaffolding |
| B-15 | Confirming every transaction over a websocket does not survive a public endpoint: the devnet run failed with `WebSocket failed to connect` after four subscriptions | `sendSetup` broadcasts over HTTP and confirms by polling `getSignatureStatuses`; a setup transaction carries a blockhash lifetime, so SOL-15 does not apply to it. `sendPayment` still uses kit's confirmers, which is what the spec mandates. A dropped confirmation socket is now classified `SUBMIT_RPC_UNAVAILABLE` instead of escaping as a raw kit error | No — confirm |
| B-14 | `Queue.expire` is specified as synchronous but has to persist what it voided | The in-memory state changes before it returns and the store write is not awaited. A crash in that window leaves a payment `queued` past its window, which the next `expire` voids again — the state is recomputable, so the race is harmless | Maybe — an async `expire` would be cleaner |
